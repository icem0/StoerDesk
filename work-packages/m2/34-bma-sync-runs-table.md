## Task

1. Add the Drizzle table `bmaSyncRuns` to `apps/api/src/db/schema.ts` exactly as the
   interfaces describe; the check constraint follows the `systemTypeCheckSql` style.
2. Generate the migration (`npm run db:generate -w @stoerdesk/api`) and keep the generated
   `0007_bma_sync_runs.sql` readable; the meta snapshot is generated, never hand-edited.
3. Test `apps/api/src/db/__tests__/bmaSyncRuns.integration.spec.ts` on the throwaway
   database: a bare insert lands with `status = 'RUNNING'`, all counters `0`,
   `conflicts = '[]'` and `finished_at is null`; an unknown status is rejected by the
   check; a run can be finished by setting `finished_at` and the counters.

## Non-goals

- No client call, no sync logic, no route (WP-M2-33, WP-M2-35, WP-M2-36).
- No retention rule for old runs and their conflicts (phase 10 privacy WP).
- No append-only trigger: a run row is written once and finished once, unlike the event
  tables of §15 Audit.
